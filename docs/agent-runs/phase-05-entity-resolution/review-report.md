## Review pass 2: re-review of repair-03 only (code-reviewer, read-only; condensed by the orchestrator)

The comma form ("Hernández‐Solana, Ángela") is not affected.
  - Frequency in dblp-1k: not countable by D.

Notes:
- **N1 (MEDIUM, policy only; needs a human decision before Part B freezes `er-v1`).** The documented claim that different common family names stay below 0.92 is false for short surnames differing by a final letter. "Wei Chen" / "Wei Cheng" sharing one ORCID gives `family_jw` 0.96, so it is ACCEPTED on exact_id with confidence 1.0; the same for Yan/Yang, Wan/Wang, Lin/Ling, Zhan/Zhang, Fan/Fang, Tan/Tang. Mitigations: the code matches the human's decision; in rootI the `family_jw` route fires zero times (agent-reported); such pairs block apart, so they arise only through a shared `x1` ORCID key. Recommendation: drop the route (`family_exact` only), or require both family strings to have at least 6 code points. Either leaves every agent-reported rootI decision unchanged and would need only an HJ7 rerun under a new label; HJ6 would not change.
- **N2 (LOW to MEDIUM, recall; blocking-key code if fixed).** "Charles Ffrench Constant" vs "Charles ffrench‐Constant" no longer block together. D's judgment: not a defect in the dash mapping and not strictly forced by the hyphen rule; the space form takes only the last token as the family, and the same split existed for the ASCII hyphen since repair-02. A space-separated compound cannot be told from a middle name, so changing the parser is the wrong fix. A fix without touching thresholds would add an alternative primary key on the last family segment (`r1|constant|c` for "ffrench constant"); it lands in `Blocking.scala` and `Hj6Blocking.scala`, needs an HJ6 and HJ7 rerun, and only adds keys, so labels collected on rootI would stay valid if it is deferred; the cost is that the queue would not sample the missed pairs. About 5 of 2192 candidates (0.2%) in dblp-1k by D's inference; likely higher on a full corpus with double surnames.
- **N3 (LOW, recall only).** "Michael Märker" / "Michael Maerker" (`family_jw` 0.8952, ä folds to a, never ae) and "Ángela Hernández" / "Ángela Hernández-Solana" (0.9125) are false CONFLICTs under the F2 rule. CONFLICT never merges. Options for later: expand umlauts to ae/oe/ue, add a family-token-containment rule, under a new policy version.
- **N4 (LOW, tools).** The model-override check compares the `--override` value, not the effective `cfg.llm.model`, so an older policy file without `erEnv` plus `SCHOLARCHAIN_ER_LLM_MODEL` is not caught; and unknown `--override` keys are written to the header and the frozen policy verbatim (a secret typed as an override value would be persisted; the code never routes the API key there). Suggested: compare `cfg.llm.model`, and restrict overrides to known keys.
- **N5 (LOW, docs).** The text saying `OrcidNameFloor` stays so a test compiles is stale. **N6 (LOW, parse edge cases).** A doubled dash gives a different family than a single dash; a name made only of particles and a family takes the first particle as a given name.

Deferrals: none is unsafe for the labeling gate; M5 must hold before Phase 06. Not verified by D: the gzipped tables (the 3 changed decisions, the Ffrench and Hernández rows, the 237 accepts), the rootI = rootI2 comparison, the CHECK 4 output, per-round ownership, and core's ORCID and title normalizers.
